# RK3588 1080p 硬件转码路数压测

> 2026-10-10 在 RK3588 板端测试 lite-nvr「RTSP 输入 → RKMPP 硬解 → RKMPP 硬编 → RTSP 输出」能同时承载多少路 1080p，并记录各档的 CPU、内存、硬件编解码负载。部署方式见 [rockchip.md](rockchip.md)。

## 结论

- 当前版本可稳定承载 **14 路** 1080p30 HEVC→H.264 硬件转码，每路都保持 30fps；16 路时两个硬件编码核约 97%，帧率掉到 28–29.5fps。
- 瓶颈是 **硬件编码器（rkvenc）**：每路约占一个编码核的 11–12%。CPU、硬件解码和内存都还有余量。
- 板上同时运行其他业务时，建议按 **12 路** 规划，给编码核和 CPU 各留约 25% 余量。
- 修复前（编码器帧队列 128 帧），nvr 内存每路约 350–400MB，12 路时被内核 OOM 杀掉；把队列改为 8 帧后，8 路内存从 2.8GB 降到约 480MB。

## 测试环境

| 项目 | 配置 |
|---|---|
| SoC | RK3588（2 个 rkvdec 解码核、2 个 rkvenc 编码核） |
| CPU / 内存 | 8 核；7.5GB 内存，无 swap |
| 系统 | Buildroot 2018.02，Linux 5.10，glibc 2.33 |
| 板上其他负载 | 讯飞录播服务（Java 应用及其进程）照常运行，空闲时系统可用内存约 4.7GB |
| nvr 版本 | Rockchip 包，内网 Ubuntu 20.04 cross 镜像构建（产物只需 glibc 2.30），`rockchip` feature 开启 |
| FFmpeg | 包内 RK FFmpeg 8.1 shared |

## 测试方法

- **源**：板上用 RK FFmpeg 把 1080p30 HEVC 测试片（约 1.95Mbps，yuv420p）`-re -stream_loop -1` 循环推到 nvr 内置 ZLM，地址 `rtsp://127.0.0.1:8554/live/src`。
- **每一路**：通过 `/api/pipe/add` 建一条管线，输入是上面的 RTSP，输出是 `net` RTSP 推回本机 ZLM，`encode` 只设码率 4Mbps，编码格式默认 h264。HEVC→H.264 必然转码，所以每路都是一次完整的硬解加一次硬编。日志确认选中 `hevc_rkmpp (hardware)` 和 `h264_rkmpp (hardware)`，没有回退到软件。
- **每档**：建好 N 条管线后采样 60 秒，每 5 秒记录一次：
  - nvr 进程的 CPU（`/proc/<pid>/stat`，单核计 100%）和 RSS；
  - 整机 CPU（`/proc/stat`，8 核合计计 100%）、可用内存（`MemAvailable`）、1 分钟负载、SoC 温度（`thermal_zone0`）；
  - 硬件编解码负载（`/proc/mpp_service/load`；默认关闭，需要先 `echo 1000 > /proc/mpp_service/load_interval`）。
- **帧率**：第 40 到 50 秒，用 ffmpeg 并发拉取所有输出流，每路 `-t 10 -c copy` 统计 10 秒内收到的帧数，30fps 对应 300–301 帧。
- **保护**：可用内存低于 800MB 就立即结束这一档并删掉管线，避免再次触发 OOM。表中数值是去掉启动第一个采样点后的平均值。

## 修复前的结果（编码器帧队列 128 帧）

| 路数 | 10 秒帧数 | nvr 内存 | 可用内存 | 整机 CPU | 编码核 0 / 1 |
|---|---|---|---|---|---|
| 1 | 301 | 142MB | 4613MB | 3% | 11% / 0 |
| 4 | 301 | 1071–1383MB | 3150–3460MB | 11% | 25% / 20% |
| 6 | 301 | 2567MB | 1820MB | 17% | 37% / 30% |
| 8 | 301 | 2830MB | 1410MB | 26% | 49% / 42% |
| 12 | 测量中 nvr 被杀 | 被 OOM 杀掉时 anon-rss 约 3.8GB | – | – | – |

原因和处理：

- 增长的内存全部是进程 heap（RssAnon），不是硬件缓冲映射。
- 每个编码器前有一个帧队列，原来上限是 128 帧，1080p 每帧约 3MB。ZLM 在客户端连接时会一次性下发缓存的 GOP，这波突发会把队列填满；FFmpeg 的解码帧缓冲池随之涨到峰值，之后只回收进池、不还给系统。
- 固定 `MALLOC_MMAP_THRESHOLD_=1048576` 只让 4 路的内存少了约 23%，所以换内存分配器（例如 jemalloc）解决不了主要问题。
- 处理方式：默认上限改为 8 帧，并支持用环境变量调整，见下节。

## 相关配置

| 环境变量 | 作用 |
|---|---|
| `FFMPEG_BUS_ENCODER_QUEUE_FRAMES` | 每个编码器前的解码帧队列长度，默认 8；必须是正整数，非法值会打警告并回退到默认值。每多 1 帧，每路约多 3MB（1080p）。直播输入时队列满了会丢帧，文件输入时会背压等待 |
| `FFMPEG_BUS_DISABLE_HWDEC=1` | 强制软件解码，用于对照测试 |

## 注意事项和局限

- 所有 RTSP 都走板内回环，而且 N 路拉的是同一个 ZLM 源，没有覆盖真实摄像头的网络抖动、丢包和多路独立连接。
- 只测了视频，没有音频；输出码率 4Mbps，H.264 默认 profile。换成 HEVC 输出、更高码率或带缩放时，每路的编码负载会不同。
- 源是 4:2:0。4:2:2 / 4:4:4 的源会跳过 RKMPP、改走软件解码（见 `hw::rkmpp_decodes`），CPU 消耗会高得多。
- 没测端到端延迟。直播输入时编码器队列最多缓存 8 帧（30fps 下约 0.27 秒）；连接 ZLM 时那波缓存帧的突发会被部分丢弃，输出从较新的帧开始。
- 16 路时温度到 63°C。长时间满载需要结合实际散热条件再验证。
- 板上同时运行着其他录播业务，它们也会占用 MPP 和 CPU；如果它们在用硬件编解码，可用路数会更少。

## 复现

1. 按 [rockchip.md](rockchip.md) 打包、部署并启动 nvr。
2. 开启 MPP 负载统计：`echo 1000 > /proc/mpp_service/load_interval`（测完写回原值，通常是 0）。
3. 用包内 RK FFmpeg 把一个 1080p30 的 HEVC 文件循环推到 `rtsp://127.0.0.1:8554/live/src`。
4. 用 `admin` 登录，取得 token 后逐路调用：
   ```bash
   curl -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' \
     -d '{"id":"cap1","input":{"t":"net","i":"rtsp://127.0.0.1:8554/live/src"},
          "outputs":[{"net":{"url":"rtsp://127.0.0.1:8554/out/cap1","format":"rtsp"},
                      "encode":{"bitrate":4000000}}]}' \
     http://<板子地址>:18080/api/pipe/add
   ```
5. 稳定后采集上面「测试方法」里的指标，并用 `ffmpeg -rtsp_transport tcp -i rtsp://127.0.0.1:8554/out/capN -t 10 -c copy -f null -` 统计各路帧数；测完调用 `/api/pipe/remove/capN` 删除。
